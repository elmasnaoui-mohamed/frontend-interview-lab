JavaScript foundations

The language mechanics behind most frontend follow-ups.

01 Scope and lexical scope

Scope controls where a variable can be accessed. JavaScript has global, function, and block scope. It uses lexical scope, so a function can access variables based on where the function was written, not where it is called.

Easy explanation

Think of nested rooms. Code in an inner room can see names in outer rooms, but outer rooms cannot see names declared only inside. The room layout is decided when the code is written.

const appName = 'Shop';

function checkout() {
  const currency = 'EUR';
  if (true) {
    const total = 40; // block scoped
    console.log(appName, currency, total);
  }
  // console.log(total); // ReferenceError
}

Common traps

  • Confusing scope with the value of this.
  • Assuming var is block scoped—it is function scoped.
  • Accidentally creating globals in old non-strict code.

Likely follow-ups

What is a scope chain? What is the temporal dead zone? How is module scope different from global scope?

02 Closures

A closure is a function together with access to the lexical environment where it was created. That means it can still use outer variables even after the outer function has finished. I use closures for private state, callbacks, and function factories.

Easy explanation

The inner function keeps a “backpack” containing the outer variables it needs.

function createCounter() {
  let count = 0;
  return () => ++count;
}

const next = createCounter();
next(); // 1
next(); // 2

The returned function keeps access to count. Each call to createCounter creates a separate private environment.

Common traps

  • Closures capture bindings, not frozen copies of values.
  • A long-lived listener can retain large objects through a closure.
  • var in loops gives callbacks one shared binding; use let.

Likely follow-ups

How can a closure cause a memory leak? How would you implement private state? Why does let fix loop callbacks?

03 Hoisting and the temporal dead zone

Hoisting is a useful mental model: declarations are processed before execution. Function declarations are callable before their line. A var exists from the start of its function and initially contains undefined. let and const also exist before their declaration, but accessing them in that period—the temporal dead zone—throws an error.

Example

sayHi();             // works
function sayHi() {}

console.log(a);      // undefined
var a = 1;

console.log(b);      // ReferenceError
let b = 2;

The engine does not literally move source code. It creates bindings during environment setup, then executes statements.

Common traps

  • Saying let and const are “not hoisted.”
  • Confusing function declarations with function expressions.
  • Using pre-declaration access as a coding style even when it works.

Likely follow-ups

Why does the TDZ exist? Are classes hoisted? What happens with function expressions?

04 var, let, and const

var is function scoped, can be redeclared, and is initialized to undefined, so I avoid it in modern code. let and const are block scoped and have a temporal dead zone. I use const by default and let only when the binding must be reassigned.

Example

const user = { name: 'Mina' };
user.name = 'Sara';      // valid: object can mutate
// user = {};            // invalid: binding cannot change

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i)); // 0, 1, 2
}

Common traps

  • const does not make an object immutable.
  • var loop callbacks share one binding.
  • Choosing let “just in case” hides reassignment intent.

Likely follow-ups

Can a const array change? How do top-level declarations behave in scripts versus modules?

05 this

For a normal function, this is mainly determined by how the function is called: as a method, with new, with call/apply/bind, or as a plain function. Arrow functions do not create their own this; they capture it lexically from the surrounding code.

Example

const user = {
  name: 'Ava',
  normal() { return this.name; },
  delayed() {
    setTimeout(() => console.log(this.name), 0);
  }
};

user.normal(); // 'Ava'
const fn = user.normal;
fn();          // undefined in strict mode

Calling fn() loses the object receiver. The arrow callback in delayed keeps the method’s this.

Common traps

  • Thinking this means “the object where the function was defined.”
  • Using an arrow as an object method when a dynamic receiver is needed.
  • Forgetting DOM listeners normally set this to the element for non-arrow callbacks.

Likely follow-ups

What is this in strict mode? What does new do? Why can’t arrow functions be constructors?

06 call, apply, and bind

All three let me control this for a normal function. call invokes immediately with separate arguments, apply invokes immediately with an array-like list, and bind returns a new function for later. bind can also pre-fill arguments.

Example

function greet(greeting, punctuation) {
  return `${greeting}, ${this.name}${punctuation}`;
}
const person = { name: 'Noor' };

greet.call(person, 'Hi', '!');
greet.apply(person, ['Hi', '!']);
const sayHi = greet.bind(person, 'Hi');
sayHi('!');

Common traps

  • Trying to change an arrow function’s lexical this.
  • Creating a new bound function when removing a listener; the reference will not match.
  • Overusing apply; spread syntax is often clearer for arguments.

Likely follow-ups

How would you implement a simple bind? What happens if a bound function is used with new?

07 Prototypes and classes

JavaScript uses prototype-based inheritance. If a property is not found on an object, the engine follows its prototype chain until it finds the property or reaches null. Class syntax is a cleaner way to define constructor functions and prototype methods; it does not replace the prototype model.

Example

class User {
  constructor(name) { this.name = name; }
  greet() { return `Hi ${this.name}`; }
}

const u = new User('Lina');
Object.getPrototypeOf(u) === User.prototype; // true
u.hasOwnProperty('name');                    // true
u.hasOwnProperty('greet');                   // false

Methods live on User.prototype, so instances share one function instead of receiving a copy.

Common traps

  • Confusing an object’s prototype with a constructor’s .prototype property.
  • Mutating built-in prototypes.
  • Using inheritance where composition is simpler.

Likely follow-ups

What does new do step by step? How does instanceof work? What is Object.create?

08 Equality and coercion

I normally use strict equality, ===, because it compares without type coercion. Loose equality, ==, applies conversion rules that can be surprising. Objects compare by reference, not by contents. Object.is is similar to strict equality but treats NaN as equal to itself and distinguishes positive and negative zero.

Example

0 == false;          // true
0 === false;         // false
[] === [];           // false: different references
NaN === NaN;         // false
Object.is(NaN, NaN); // true

// One intentional loose-equality idiom:
value == null;       // true only for null or undefined

Common traps

  • Deep-comparing objects with ===.
  • Forgetting that NaN is not equal to itself.
  • Saying loose equality is random; it follows defined rules, but readability suffers.

Likely follow-ups

What values are falsy? Why is typeof null “object”? When would loose equality be acceptable?

09 Shallow vs deep copy

A shallow copy creates a new top-level object but keeps references to nested objects. Spread syntax and Object.assign are shallow. A deep copy recursively duplicates the value graph. In the browser I prefer structuredClone for supported data types, but I first ask whether a full deep copy is really needed.

Example

const original = { profile: { city: 'Rabat' } };
const shallow = { ...original };
shallow.profile.city = 'Casa';
console.log(original.profile.city); // 'Casa'

const deep = structuredClone(original);
deep.profile.city = 'Agadir';       // original unchanged

structuredClone handles cycles, Maps, Sets, Dates, and typed arrays, but it cannot clone functions or DOM nodes.

Common traps

  • Calling spread syntax a deep clone.
  • Using JSON stringify/parse: it loses types and fails on cycles.
  • Cloning huge state trees when structural sharing would be cheaper.

Likely follow-ups

What can structuredClone copy? What is structural sharing? How would you update one nested field?

10 Immutability

Immutability means producing a new value instead of changing an existing one. In UI state it makes changes predictable, supports cheap reference checks, and helps debugging. I do not treat it as a universal rule: local mutation inside a controlled function can be simpler and faster, as long as shared state is not mutated unexpectedly.

Example

const state = {
  user: { name: 'Sam', preferences: { theme: 'light' } }
};

const next = {
  ...state,
  user: {
    ...state.user,
    preferences: { ...state.user.preferences, theme: 'dark' }
  }
};

Only the changed path gets new objects; unchanged branches can keep their references. This is structural sharing.

Common traps

  • Shallow-copying the root, then mutating a nested object.
  • Deep-cloning everything and creating unnecessary CPU and memory cost.
  • Assuming Object.freeze is recursive—it is shallow.

Likely follow-ups

Why does React benefit from immutability? What is structural sharing? When is mutation acceptable?

Async JavaScript & architecture

How work is scheduled, composed, limited, and packaged.

11 Promises

A Promise represents the eventual result of an asynchronous operation. It starts pending and settles once as fulfilled or rejected. then, catch, and finally return new promises, so I can compose work and centralize error handling instead of nesting callbacks.

Example

fetch('/api/user')
  .then(response => {
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    return response.json();
  })
  .then(user => render(user))
  .catch(error => showError(error))
  .finally(() => hideSpinner());

A handler may return a plain value or another promise. The next link waits and adopts that result.

Common traps

  • Forgetting to return a promise inside then.
  • Assuming fetch rejects for HTTP 404 or 500—it normally does not.
  • Mixing callbacks and promises into hard-to-follow control flow.

Likely follow-ups

What is promise chaining? How do rejections propagate? Can a settled promise change state?

12 async/await

async/await is syntax over promises that makes asynchronous control flow read more like synchronous code. An async function always returns a promise. await pauses that function, not the JavaScript thread, and resumes it in a microtask when the value settles.

Example: sequential vs concurrent

// Sequential: second starts after first finishes
const user = await getUser();
const posts = await getPosts();

// Concurrent: both start immediately
const [user, posts] = await Promise.all([
  getUser(), getPosts()
]);

try {
  const data = await loadData({ signal });
} catch (error) {
  if (error.name !== 'AbortError') report(error);
}

Common traps

  • Serializing independent calls with back-to-back await.
  • Using forEach(async ...); it does not await callbacks.
  • Assuming a promise can be cancelled; cancellation must be designed, often with AbortController.

Likely follow-ups

How do you run tasks concurrently? How do you handle partial failure? How would you limit concurrency?

13 Event loop, microtasks, and tasks

JavaScript runs one call stack per main thread. The browser handles timers, network events, and user input outside that stack and queues callbacks. After the current task finishes, the browser drains the microtask queue—promise handlers and queueMicrotask—before it may render and take the next task, such as a timer or click.

Predict the output

console.log('A');

setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
queueMicrotask(() => console.log('D'));

console.log('E');
// A, E, C, D, B

The current script is one task. Microtasks run in registration order after it completes. The timer is a later task.

Common traps

  • Saying setTimeout(..., 0) runs immediately.
  • Calling every task a “macrotask”; the HTML spec generally says task.
  • Creating an endless microtask chain that starves rendering and input.

Likely follow-ups

Where does rendering happen? What does requestAnimationFrame do? Can microtasks starve the page?

14 Promise.all and combinators

Promise.all runs independent operations concurrently and fulfills with ordered results when all fulfill. It rejects as soon as one input rejects, although the other operations keep running. For partial success I use allSettled; for the first settled result, race; and for the first fulfilled result, any.

Example

const [profile, permissions] = await Promise.all([
  fetchProfile(),
  fetchPermissions()
]);

const results = await Promise.allSettled(urls.map(fetchJson));
const successful = results
  .filter(r => r.status === 'fulfilled')
  .map(r => r.value);

“Fail fast” does not mean cancellation. Use abort signals if the remaining work should be stopped.

Common traps

  • Thinking Promise.all itself starts promises; operations usually start when created.
  • Passing functions instead of calling them.
  • Launching thousands of requests without a concurrency limit.

Likely follow-ups

Does result order follow completion order? How would you add a timeout? How would you limit to five requests at once?

15 Debounce and throttle

Debounce waits until calls stop for a period, so it is useful for search input or validation. Throttle limits execution to at most once per interval, so it suits scroll, resize, or pointer updates. The production choice also needs leading/trailing behavior, cancellation, argument handling, and cleanup.

Simple implementations

function debounce(fn, delay) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

function throttle(fn, interval) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= interval) {
      last = now;
      fn.apply(this, args);
    }
  };
}

Common traps

  • Recreating the wrapped function on every render.
  • Not clearing timers when a component unmounts.
  • Ignoring the final call in a naive throttle.
  • Using a timer for visual animation where requestAnimationFrame fits better.

Likely follow-ups

What are leading and trailing calls? How do you add cancel/flush? Which would you use for autocomplete?

16 Modules

ES modules use static import and export, have their own scope, run in strict mode, and let bundlers analyze dependencies for tree-shaking. Dynamic import() loads code on demand and returns a promise. In browsers, modules are deferred by default and imported bindings are live, read-only views.

Example

// math.js
export const add = (a, b) => a + b;

// app.js
import { add } from './math.js';

button.addEventListener('click', async () => {
  const { openEditor } = await import('./editor.js');
  openEditor();
});

Dynamic import is a common route- or feature-level code-splitting boundary.

Common traps

  • Assuming tree-shaking can always remove code with side effects.
  • Creating circular dependencies that read an uninitialized binding.
  • Confusing ESM’s live bindings with copied values.

Likely follow-ups

ESM vs CommonJS? What enables tree-shaking? What are circular dependency risks?

17 Error handling

I handle errors at the level that can add context, recover, retry, or show the right UI. I throw Error objects, preserve the original cause, distinguish expected domain errors from programmer bugs, and avoid swallowing failures. At application boundaries I log useful context without exposing secrets.

Example

class ApiError extends Error {
  constructor(message, { status, cause } = {}) {
    super(message, { cause });
    this.name = 'ApiError';
    this.status = status;
  }
}

try {
  return await saveOrder(order);
} catch (error) {
  throw new ApiError('Could not save order', { cause: error });
}

try/catch catches synchronous throws and rejected promises that are awaited inside the block.

Common traps

  • catch {} silently hides production failures.
  • Throwing strings loses standard stack and metadata behavior.
  • Retrying non-idempotent operations or permanent 4xx failures blindly.

Likely follow-ups

What can an error boundary catch? When should you retry? How do global unhandled rejection handlers fit in?

18 Memory leaks

A memory leak happens when the app keeps references to data it no longer needs, so garbage collection cannot reclaim it. In frontend apps I look for unremoved listeners, timers, subscriptions, detached DOM nodes, unbounded caches, and closures retaining large graphs. I verify with heap snapshots and allocation timelines instead of guessing.

Example and cleanup

const controller = new AbortController();

window.addEventListener('resize', onResize, {
  signal: controller.signal
});
const timer = setInterval(refresh, 30_000);

function cleanup() {
  controller.abort(); // removes listener
  clearInterval(timer);
}

WeakMap can associate metadata with objects without keeping the key alive, but it is not a general replacement for explicit cleanup.

Common traps

  • Calling high memory use a leak without checking whether it remains reachable.
  • Removing a listener with a different function reference.
  • Keeping every API response forever in a cache.

Likely follow-ups

How does garbage collection decide reachability? What are detached DOM nodes? When would you use WeakMap?

Browser platform & performance

DOM events, pixels, performance, and inclusive interfaces.

19 DOM and events

The DOM is the browser’s object model of the document. Event propagation normally has capture, target, and bubble phases. I often use event delegation: one listener on a stable ancestor handles matching descendants. That reduces listeners and works for dynamically added elements.

Example

const list = document.querySelector('[data-list]');

list.addEventListener('click', event => {
  const button = event.target.closest('[data-remove]');
  if (!button || !list.contains(button)) return;
  removeItem(button.dataset.remove);
});

Use currentTarget for the element whose listener is running; target is where the event originated.

Common traps

  • Confusing target and currentTarget.
  • Using stopPropagation broadly and breaking other behavior.
  • Repeated layout reads and writes in loops.
  • Using non-passive scroll listeners without need.

Likely follow-ups

Capture vs bubble? Which events do not bubble? What is the difference between DOM attributes and properties?

20 Browser rendering pipeline

At a high level, the browser parses HTML into the DOM and CSS into the CSSOM, combines them into a render tree, calculates layout, paints pixels into layers, and composites those layers on screen. JavaScript and style changes can invalidate parts of that work, so I measure and avoid doing expensive work repeatedly in a frame.

Easy sequence

HTML ──> DOM ─┐
              ├─> Render tree ─> Layout ─> Paint ─> Composite
CSS  ──> CSSOM┘

Modern engines optimize aggressively, so this is a conceptual model, not a promise that every frame executes every stage. Parsing scripts can block HTML parsing unless loading strategy such as defer or modules is used.

Common traps

  • Presenting the pipeline as a rigid full-page sequence for every change.
  • Assuming every JavaScript execution blocks all downloads.
  • Optimizing from theory without using DevTools performance traces.

Likely follow-ups

What blocks first render? What do async and defer do? What is the critical rendering path?

21 Reflow, repaint, and compositing

A layout or reflow recalculates geometry. Paint redraws visual pixels such as color or shadow. Compositing combines already-painted layers, often on the compositor thread. For smooth animation I prefer transform and opacity when appropriate, and I batch DOM reads and writes to avoid forced synchronous layout.

Layout thrashing

// Bad: write then layout read on every iteration
items.forEach(item => {
  item.style.width = '200px';
  console.log(item.offsetWidth);
});

// Better: group reads, then writes
const widths = items.map(item => item.offsetWidth);
requestAnimationFrame(() => {
  items.forEach((item, i) => {
    item.style.transform = `translateX(${widths[i]}px)`;
  });
});

Common traps

  • Saying transform is always free; large layers use memory and still need compositing.
  • Adding will-change everywhere.
  • Mixing geometry reads and style writes repeatedly.

Likely follow-ups

Which properties trigger layout? What causes forced layout? Why can too many layers hurt?

22 Accessibility

Accessibility means people can perceive, understand, navigate, and operate the interface with different abilities and tools. I start with semantic HTML, keyboard access, visible focus, correct labels, useful headings and landmarks, sufficient contrast, and predictable error messages. I use ARIA only when native HTML cannot express the behavior.

Example

<label for="email">Email</label>
<input id="email" name="email" type="email"
       aria-describedby="email-error" required>
<p id="email-error" role="alert"></p>

<button type="button">Save</button>
<!-- not: <div onclick="save()">Save</div> -->

Testing includes keyboard-only navigation, a screen reader smoke test, zoom, automated checks, and real user feedback where possible.

Common traps

  • Using ARIA to repair avoidable non-semantic markup.
  • Removing focus outlines without an equivalent.
  • Using placeholder text as the only label.
  • Assuming automated tools catch all accessibility issues.

Likely follow-ups

How do you manage focus in a modal? What is an accessible name? When should aria-live be used?

23 Web Vitals

The core user-centered metrics are LCP for loading, INP for interaction responsiveness, and CLS for visual stability. I use real-user monitoring as the source of truth and lab tools for diagnosis. I improve the actual bottleneck—for example the LCP resource, long main-thread tasks, or elements without reserved space—rather than chasing one score.

Practical improvements

  • LCP: optimize and prioritize the hero image, reduce server delay, remove render blockers.
  • INP: shorten event work, split long tasks, reduce unnecessary rendering, avoid heavy synchronous JS.
  • CLS: reserve image/ad dimensions, avoid inserting content above, load fonts carefully.
new PerformanceObserver(list => {
  for (const entry of list.getEntries()) {
    sendMetric(entry);
  }
}).observe({ type: 'long-animation-frame', buffered: true });

Common traps

  • Using only Lighthouse lab data as proof of real-user experience.
  • Confusing FCP with LCP.
  • Optimizing averages while ignoring poor p75 experiences and device segments.
  • Treating metric improvements as a substitute for usability.

Likely follow-ups

Field vs lab data? How do you find the LCP element? What causes poor INP? Why measure p75?

Networking, identity & security

How the browser communicates, stores trust, and protects users.

24 Networking: from URL to page

At a high level, the browser resolves the hostname with DNS, establishes a connection—TCP plus TLS for HTTP/1.1 or HTTP/2, or QUIC with TLS for HTTP/3—sends the HTTP request, receives the response, and then parses and renders resources. Caches, service workers, connection reuse, redirects, and proxies can change that path.

Easy sequence

URL → cache/service worker → DNS → connection + TLS
    → HTTP request → server/CDN → HTTP response
    → parse → fetch subresources → render

HTTP/2 multiplexes streams over one connection. HTTP/3 uses QUIC over UDP to reduce some transport-level blocking and improve connection setup.

Common traps

  • Saying HTTP/2 removes all head-of-line blocking; TCP loss still affects the connection.
  • Forgetting connection reuse and browser caches.
  • Assuming DNS always means one fresh remote lookup.

Likely follow-ups

HTTP/2 vs HTTP/3? What happens in a TLS handshake? What is a CDN? What is a service worker’s role?

25 HTTP

HTTP is a stateless request-response protocol. A request has a method, URL, headers, and optional body; a response has a status, headers, and optional body. I choose methods by semantics—GET reads, POST commonly creates or triggers work, PUT replaces, PATCH partially updates, and DELETE removes—and I design retries around idempotency.

Useful status groups

  • 2xx: success—200 OK, 201 Created, 204 No Content.
  • 3xx: redirection or cache—301/308 permanent, 302/307 temporary, 304 Not Modified.
  • 4xx: client-side condition—400, 401 unauthenticated, 403 forbidden, 404, 409, 429.
  • 5xx: server failure—500, 502, 503, 504.
const response = await fetch('/api/items/42', {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ archived: true })
});

Common traps

  • Saying 401 means “not authorized”; it usually means authentication is required or invalid.
  • Retrying POST without idempotency protection.
  • Putting secrets in query strings and logs.

Likely follow-ups

PUT vs PATCH? Safe vs idempotent methods? 401 vs 403? What does content negotiation mean?

26 HTTP caching

HTTP caching avoids unnecessary transfers. Cache-Control defines freshness and storage rules. While a response is fresh, it can be reused directly; when stale, validators such as ETag or Last-Modified allow revalidation and a 304 response. For versioned static assets I use long immutable caching; HTML usually needs a shorter or revalidated policy.

Typical policies

# Fingerprinted asset: app.a1b2c3.js
Cache-Control: public, max-age=31536000, immutable

# HTML that should be checked before reuse
Cache-Control: no-cache
ETag: "page-v42"

# Sensitive response: do not store
Cache-Control: no-store

no-cache means “revalidate before reuse,” not “do not store.” Vary tells caches which request headers affect the representation.

Common traps

  • Confusing no-cache with no-store.
  • Caching HTML forever and trapping users on old asset references.
  • Forgetting shared-cache privacy and Vary.

Likely follow-ups

Strong vs weak ETags? Browser cache vs CDN vs service worker cache? How do you invalidate assets?

27 CORS

CORS is a browser mechanism that lets a server opt into cross-origin reads. The same-origin policy normally blocks frontend JavaScript from reading another origin’s response. For some requests the browser first sends an OPTIONS preflight. CORS is enforced by browsers; it is not authentication and it does not stop direct server-to-server requests.

Credentialed example

fetch('https://api.example.com/profile', {
  credentials: 'include'
});

// Response must use a specific origin, not *, for credentials:
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true

An origin is the combination of scheme, host, and port. “Simple” requests can skip preflight, but their response still needs the correct CORS headers to be readable.

Common traps

  • Trying to fix CORS from client JavaScript.
  • Using wildcard origin with credentials.
  • Calling CORS a security boundary for the API itself.
  • Forgetting that preflight responses need correct headers too.

Likely follow-ups

What triggers preflight? What is a simple request? CORS vs CSRF? Why can a form still send cross-origin?

28 Cookies and browser storage

Cookies are small values automatically attached to matching HTTP requests, so they suit server sessions but need security attributes. localStorage persists by origin and is synchronous; sessionStorage is scoped to an origin and tab session. IndexedDB is asynchronous and better for larger structured offline data. I choose storage based on lifecycle, size, access pattern, and threat model.

Secure session cookie

Set-Cookie: session=opaque-value;
  HttpOnly; Secure; SameSite=Lax; Path=/
  • HttpOnly: JavaScript cannot read it.
  • Secure: send only over HTTPS.
  • SameSite: limits cross-site sending and helps against CSRF.

Common traps

  • Storing sensitive long-lived tokens in localStorage without considering XSS.
  • Using synchronous storage in a hot path.
  • Assuming HttpOnly cookies eliminate CSRF.
  • Storing secrets client-side as if users cannot inspect them.

Likely follow-ups

Cookie vs localStorage for auth? What does SameSite do? When would you use IndexedDB? What are storage quotas?

29 Authentication vs authorization

Authentication answers “who are you?” and authorization answers “what are you allowed to do?” Authentication might use a password, passkey, or identity provider. After identity is established, the server applies authorization rules for every protected action. Frontend route guards improve UX, but they are never the real security boundary.

Practical model

Sign in → establish identity → issue session/token
Request → validate session/token → load policy/roles
        → authorize this resource and action → allow/deny

Role-based access control is convenient, but resource ownership or attribute-based rules are often required. The server must enforce them.

Common traps

  • Hiding a button and calling the action secure.
  • Confusing OAuth authorization with user authentication; OpenID Connect adds an identity layer.
  • Trusting role or price values supplied by the client.

Likely follow-ups

Sessions vs tokens? OAuth vs OpenID Connect? RBAC vs ABAC? Where should permission checks live?

30 JWT and refresh flow

A JWT is a signed token format, not an authentication strategy by itself. A common flow uses a short-lived access token for APIs and a longer-lived refresh token to obtain new access tokens. I prefer refresh tokens in Secure, HttpOnly, appropriately SameSite cookies, rotate them on use, detect reuse, and keep access tokens short-lived.

Refresh flow

1. Sign in successfully
2. Server returns short-lived access token
   and sets protected refresh-token cookie
3. API call receives 401 because access token expired
4. Client calls /auth/refresh once
5. Server validates + rotates refresh token
6. Client retries queued requests with new access token
7. If refresh fails, clear session and ask user to sign in

Coordinate concurrent 401 responses so only one refresh runs. Decode a JWT only to read claims; signature validation and authorization belong on the server.

Common traps

  • Assuming encoded JWT payloads are encrypted or secret.
  • Putting long-lived tokens in JavaScript-readable storage.
  • Creating an infinite 401 → refresh → retry loop.
  • Refreshing separately for every concurrent failed request.
  • Not planning revocation, rotation, clock skew, or logout.

31 XSS, CSRF, and CSP

XSS lets attacker-controlled code run in the site’s origin, so I prevent it with contextual output encoding, safe DOM APIs, sanitization for allowed HTML, and a restrictive CSP as defense in depth. CSRF tricks a browser into sending an authenticated request, so I use SameSite cookies, CSRF tokens or origin checks, and safe request design. CSP limits which scripts and resources may execute or load.

Safer patterns

// Safe for plain text
element.textContent = untrustedValue;

// Dangerous without robust sanitization
element.innerHTML = untrustedValue;

Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m';
  object-src 'none'; base-uri 'self';

XSS can bypass many CSRF defenses because malicious code runs inside the trusted origin. Framework escaping helps, but unsafe HTML escape hatches still need care.

Common traps

  • Treating CSP as the only XSS defense.
  • Using regex as an HTML sanitizer.
  • Assuming JSON APIs cannot have CSRF risk.
  • Allowing 'unsafe-inline' and calling the CSP strong.
  • Logging tokens or personal data to analytics.
